- 코드 및 파일의 생성, 수정, 패치 등을 진행하기 전 유저의 허락을 받아라. 즉, 사용자가 확실하게 '코드를 패치하라'라고 지시한 경우에만 코딩을 진행하라.
- 하드코딩을 지양하고, 추후에 언제든 유연하게 수정 및 확장 등 패치가 가능하도록 코드를 짜라.
- **Comment Policy**: Every code patch must include clear, detailed comments explaining its purpose. This is to ensure any future maintainer can easily understand the code.
- 사용자의 프롬프트에 따라서 코드를 패치하기 전, 냉정하게 사용자의 아이디어에  모순된 정보가 있거나 예상되는 버그 가능성 등 문제가 생길만한 부분을 판단하고, 사용자에게 미리 경고해야 한다고 판단되면 바로 패치를 진행하지 말고 '이런 문제가 예상된다'라고 미리 말하라.
- 패치 시 특정 코드 파일이 너무 길어질 것 같거나, 이미 너무 길게 코딩된 것을 발견하여 환각이나 truncation의 위험이 높아지면 먼저 '리팩토링이 필요할 것 같다'고 말해달라.
- 패치 이후에는 패치한 내용이 정상작동하는지 확인할 수 있는 '디버깅 목록' 제시하라.

# 🔍 브라우저 디버깅 및 토큰 절약 지침

1. **콘솔 로그 우선 조회**:
   - 브라우저 상에서 동작 에러나 화면 오류가 의심될 경우, 무의미한 페이지 스크롤이나 `view-source:` 주소 접속을 엄격히 금지합니다.
   - 에러가 나면 1순위로 브라우저 콘솔 로그 수집 도구(`capture_browser_console_logs`)를 1회 실행하여 에러 메시지와 콜 스택(오류 줄 번호)을 먼저 수집해야 합니다.

2. **로컬 소스 코드 직접 디버깅**:
   - 에러 위치(파일명, 라인)가 확인되면 브라우저 내부에서 추가적인 검색 작업을 멈추고, 즉시 로컬 개발용 파일(`src/` 폴더 내 원본 소스)을 직접 열어 코드를 대조하고 오류를 패치합니다.

3. **연속 실패 시 즉시 중단 및 보고**:
   - 브라우저 페이지 열기(`open_browser_url`)나 버튼 클릭 등 동일한 브라우저 인터랙션 실패가 2회 이상 연속으로 감지되면, 무작위 포트 스캐닝이나 우회 시도를 완전히 중단하고 즉시 사용자에게 현황을 보고하여 해결 방안을 묻습니다.
